# Spec（功能规约文档）通用模板

> 本文档是一份**语言、技术栈、项目类型无关**的 spec 写作模板，适用于任何需要"先设计后编码"的软件功能改动。
> 它融合了业界 spec 实践（User Stories 驱动验收、测试 seam 经济学、决策与实现分层）与团队沉淀，可作为任何项目的 spec 起始骨架。
>
> **核心信念**：spec 的价值不在"记录将要发生什么"，而在**强制作者在写代码前把问题想清楚**。一份好的 spec 能让另一个工程师（或 AI）在没有作者在场的情况下，独立实现并验证功能。

---

## 〇、Spec 是什么 / 不是什么

| Spec **是** | Spec **不是** |
|---|---|
| 设计阶段的决策记录 | 代码注释的扩充版 |
| 验收标准的载体 | 详细设计文档（DDD）的替代 |
| 团队知识沉淀（done 后兼做历史档案） | 用户手册 / API 文档 |
| 沟通对齐工具 | 一次性用完即弃的草稿 |

**关键区分**：spec 写"**做什么决策、为什么**"，不写"具体在哪个文件的哪一行加什么代码"。后者属于实现，会随重构过时；前者属于设计，重构后仍成立。

---

## 一、何时需要写 Spec

判定标准：**改动会触及多个模块 / 引入新接口 / 改变既有行为 / 涉及外部契约**。满足任一条即应写：

- 新增对外接口（HTTP / RPC / CLI 命令 / 导出 API），或改动现有接口的契约
- 改动持久化层 schema（数据库表/字段/索引、配置文件结构、消息格式）
- 跨多个模块/包的逻辑修改
- 引入新依赖、新外部服务调用
- 改变既有功能的可见行为（哪怕只是默认值、错误提示语义）
- 安全相关改动（鉴权、权限、数据隔离）

**不需要写 spec**（直接编码）：

- 单函数 bug 修复，验收标准一句话能说清
- 纯重构（不改外部行为），且改动局限在单文件
- 文案、注释、配置值微调

> **边界模糊时倾向写。** Spec 写完发现自己把问题想复杂了，是收益（说明你想清了）；直接动手发现想浅了，是返工。

## 二、Spec 与开发流程的关系

```
需求提出
   │
   ▼
[需求是否明确?] ──否──▶ 澄清：主动挖掘验收标准、优先级、范围
   │是
   ▼
[是否"较大改动"?] ──否──▶ 直接编码 + 自测
   │是
   ▼
写 Spec（drafting）────────────────┐
   │                                │ 方案段写完
   ▼                                ▼
与协作者对齐方案 ──有分歧──▶ 修订 Spec（仍 drafting）
   │对齐
   ▼
状态 → implementing，开始编码
   │
   ▼
按「验证方案」逐项验证
   │全通过
   ▼
填写「实测结果」，状态 → done
```

## 三、命名与组织

### 命名

```
YYYY-MM-DD-<kebab-case-主题>.<ext>
```

- 日期用**创建日**，一份 spec 一个文件
- 主题用英文 kebab-case，简短点出改动核心
- 示例：`2026-08-01-session-history-api.md`、`2024-03-15-payment-retry.md`、`2025-11-20-rate-limiter.md`

### 组织

- 集中存放在项目的 `spec/`（或 `docs/spec/`、`design/`）目录
- 用 `README.md` 索引本目录的 spec 规范（命名/状态流转/模板）；项目的开发规范文档（如 `AGENTS.md` / `CONTRIBUTING.md`）只写"何时写 spec"的触发规则，指向此 README，**不重复模板内容**（避免两处漂移）

## 四、状态流转

文档头部的 `状态:` 字段，三态：

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `drafting` | 设计中，方案未定稿 | 创建时默认 |
| `implementing` | 方案已确认，编码中 | 与协作者对齐方案后 |
| `done` | 代码完成 + 验证通过 | 「验证方案」段每个 case 都有实测结果 |

**done 的硬门槛**：验证方案段列出的每个 case 必须有实测结果（数据/截图/日志），记到「实测结果」段。未验证的不能标 done——状态不可作为"我觉得应该没问题"的掩护。

状态只前进不回退。方案推翻就新开 spec，两份头部互相关联。

## 五、模板正文

> 复制下方内容作为新 spec 的起始骨架。带 ★ 的段是提升 spec 质量的关键段，尽量写满；
> 标「可选」的段按改动复杂度决定是否写。段顺序即推荐阅读顺序。

```markdown
# <一句话标题：动作 + 对象 + 关键特征>

> 状态：drafting
> 创建：YYYY-MM-DD
> 关联：<前置/同期 spec、调研材料、相关 issue；没有可省略此行>

## 背景

从**用户/业务视角**描述痛点，不是从代码视角。
引用具体证据：当前行为的实测数据、报错信息、badcase 复现。
点出根因（一句话），不展开论证——论证放方案段。

【示例】
用户反馈"复杂问题答不全"。实测发现：当前检索固定返回 3 条结果，
跨 3 个文档的对比类问题只能命中 1 个文档的片段，另 2 个文档的关键
信息未被召回。根因：检索数量固定，不随问题复杂度调整。

## ★ User Stories

穷举本次功能涉及的所有交互路径，每条一行：

- 作为 <角色>，我想 <动作>，以便 <目的>。

角色可以是：终端用户、前端、其他服务、运维、系统本身。

【自检规则】
1. 写完方案后回看：所有「边界 case」应能映射到某条 story。
   - 边界 case 找不到 story → story 漏了，补
   - story 没产生任何边界 case → 可能是 out of scope，确认
2. 列全的标准不是"我能想到几条"，而是"再想不出新的交互路径"。

【示例】
- 作为终端用户，我想看到历史会话列表，以便切换不同对话。
- 作为终端用户，我想看到每条会话的最后消息预览，以便快速识别内容。
- 作为系统，我想按用户隔离数据，以便 A 看不到 B 的数据。

## 目标 / 非目标（可选，复杂改动必写）

**目标**：本次要做到什么（可验收的几条）
**非目标**：明确划出本次不做的，避免 scope creep

非目标的价值：后续维护者能据此判断"这个没做是设计决策还是遗漏"。

## ★ 方案

核心技术决策。**只写决策和理由，不写文件路径和代码骨架**——
文件会重构、代码会改，写死会过时。

### 决策表（推荐形式）

| 决策点 | 选择 | 理由 |
|---|---|---|

【为什么禁止代码骨架】
代码骨架会制造"已经设计完了"的错觉，实际它只表达了位置不表达决策。
更糟的是重构后它变成谎言，误导后来者。
例外：决策密集、文字难以精确表达时（状态机、数据 schema、类型形状、
复杂 SQL/正则），可内联精简片段并注明来源，但只保留决策密集的部分。

### 外部依赖（涉及框架/第三方/外部服务时必写）

查证过的契约、API 文档、源码位置（带精确版本/行号/链接）。
这一段是"动手前先查证"的落地产物，便于实施时回查，也便于方案失效时溯源。

## 边界 case

逐条列出异常/边界路径，每条配预期行为。
**来源**：应从 User Stories 推导，不要凭空补。每条 case 标注对应的 story。

【示例】
- (对应 story 3) 跨用户访问：用户 A 用 B 的资源 ID 查询 → 返回 404（防枚举，数据隔离）
- (对应 story 2) 预览内容超长 → 截断到 100 字符并追加 "..."

## ★ 验证 seam（测试决策）

显式记录测试入口的选型，这是一个独立的工程决策：

- **测试 seam**：<HTTP / 接口层 / 业务层 / 单元>（选能覆盖验收点的最高层）
- **复用入口**：<现有测试脚本/工具/测试文件，没有写"无">
- **新建入口**：<必须新建时的理由；能用现有就不新建>

【测试 seam 经济学】
- 优先复用现有 seam，能用高层 seam 就不拆到低层
- 全功能理想 seam 数 = 1：一个入口覆盖所有验收点
- 每新建一个测试入口都要在本段说明"为什么现有的不够"
- 选 seam 的原则：测外部行为，不测实现细节——实现会变，行为契约稳定

## 验证方案

逐条列出验证 case（与边界 case、User Stories 对应），每条可勾选。
这些是 done 的判定依据，写不出可勾选的 case = 验收标准不清晰。

【示例】
- [ ] 正常路径：合法请求 → 返回正确数据结构
- [ ] 边界：不存在的 ID → 返回 404
- [ ] 隔离：跨用户访问 → 返回 404
- [ ] 回归：不传新参数 → 行为与改动前一致（向后兼容）

## 不在本次范围（Out of Scope）

明确列出，便于后续 spec 接续。
判定规则：不在任何 User Story 里的 = out of scope。

## ★ 实测结果（done 时必填）

### 改动清单

- 新增/修改的文件/模块（一句话职责，不贴代码）

### 验证 case 结果

| 测试 | 结果 |
|---|---|

### 实施中发现的问题（可选）

踩坑、与方案的偏差、修复过程。
这一段是知识沉淀的关键——方案段写的是"预期"，这里写的是"现实"，
两者偏差处往往藏着最值得记录的认知。
```

## 六、写作原则（贯穿全段）

### 1. 决策与实现分层

| 段 | 写什么 | 不写什么 |
|---|---|---|
| 方案 | 决策 + 理由（"用模糊匹配不用全文索引，因为数据量小"） | 文件路径、代码骨架 |
| 实测结果·改动清单 | 文件/模块职责（"新增 handler，负责分流"） | 代码实现 |
| 外部依赖 | 精确位置（源码行号、API 文档链接、版本号） | 模糊的"框架支持" |

**理由**：方案段在重构后仍要有效；实现细节会过时。把它们分层，让 spec 的"设计价值"与"实现记录"各自归位。

### 2. 查证优先，禁止编造

具体名字、版本号、API 签名、行号、外部链接——必须查证后再写。给不出处就不写，不确定就说"待查证"。

### 3. 业务语言，不暴露实现细节

spec 是面向协作的文档，用业务/领域语言描述。密钥、DSN、内部 IP 等敏感信息不得写入（spec 会进版本库）。

### 4. 倾向澄清，不擅自设计

需求不明确时主动澄清，对齐验收标准。不要把"用户没说"当成"用户要我自由发挥"——多个合理解读并存时，呈现选项让用户选，不静默选一个。

## 七、自检清单（写完 spec 后逐项过）

发布 spec 前自查：

- [ ] **背景**有具体证据（数据/报错/badcase），不是空泛描述
- [ ] **User Stories** 穷举了交互路径，且能覆盖所有边界 case
- [ ] **方案**只写决策不写代码骨架，决策都有理由
- [ ] **外部依赖**带精确出处（版本/行号/链接），不是"框架支持"
- [ ] **边界 case** 每条都能映射到某条 User Story
- [ ] **验证 seam** 显式选了入口，新建入口有理由
- [ ] **验证方案** 每条可勾选、可执行
- [ ] **Out of Scope** 明确，与 User Stories 边界清晰
- [ ] 全文无密钥/DSN/内部 IP 等敏感信息
- [ ] 无未经查证的具体名字/版本号/链接

## 八、常见误区

| 误区 | 后果 | 纠正 |
|---|---|---|
| 把 spec 写成代码注释扩充版（贴满代码骨架） | 重构后过时，成谎言 | 方案段只写决策，代码挪到实测结果·改动清单 |
| 跳过 User Stories 直接写方案 | 边界 case 靠事后回忆补，漏多 | User Stories 先行，边界 case 从 stories 推导 |
| 验证方案写"测试通过"而非可勾选 case | done 状态无客观判据 | 每条 case 可独立勾选，带明确输入和预期 |
| 外部依赖写"框架支持 XXX"无出处 | 方案失效时无法溯源 | 带版本号 + 源码行号或官方文档链接 |
| 标 done 但未填实测结果 | 状态失去公信力 | done 硬门槛：每条验证 case 有实测证据 |
| 用"我觉得应该没问题"替代验证 | 把假设当事实 | 验证方案是 done 的判定依据，不是建议 |
| 把 spec 当用完即弃的草稿 | 团队知识无法沉淀 | done 后的 spec 是历史档案，实测结果段尤其有价值 |
| 每次都新建测试入口 | 测试入口无序增长 | 验证 seam 段强制决策，理想 seam 数 = 1 |
